# V6.9 Roadmap: Organization, Quotas, and Controlled Automation

V6.8 establishes recovery, auditing, password abuse protection, and storage health checks. V6.9 should improve daily file management without turning LinkNest into a desktop-sync or online-office suite.

## Research conclusion

The next useful capabilities are lightweight organization, accountable usage, and scoped automation. They should be delivered as separate milestones because they change different ownership and data-lifecycle boundaries.

1. **Logical organization first.** Add tags, favorites, and structured filters before changing object paths or introducing physical directory moves.
2. **Quota accounting second.** Establish an explicit accounting rule before enforcing any limit, especially where deduplication or guest uploads exist.
3. **Scoped API keys third.** Replace the single site-wide upload token with revocable, hashed, named keys that can be limited to the smallest useful capability.
4. **Upload requests after ownership is clear.** A request link must never allow a contributor to browse existing files or inherit unrelated permissions.
5. **Keep search metadata-first.** Filename, extension, time, size, owner, tag, and share status cover most LinkNest use cases. PDF/Office full-text indexing stays optional because it needs an index service and reindex operations.

This direction aligns with the way mature self-hosted storage products separate tags/favorites, quotas, public-link protection, audit, and optional full-text indexing rather than putting every concern in the upload request path.

## V6.9-A: Tags, Favorites, and Filtered Search

### Scope

- Add user-owned tags and a favorite marker for files/shares.
- Add filters for filename, extension, upload time, size range, owner, tag, share status, and recycle-bin state.
- Add an administrator search view that does not expose private link passwords, raw client IPs, or API secrets.

### Data model

- `pre_tag`: `id`, `uid`, `name`, `color`, `created_at`.
- `pre_file_tag`: `file_id`, `tag_id`, with a unique pair.
- `pre_file_favorite`: `file_id`, `uid`, `created_at`, with a unique pair.

Tags are logical metadata. They must not change the object-storage key, reupload a file, or break existing short links.

### Acceptance

- A user can add/remove a tag and favorite without changing the share URL.
- A tag belonging to one user is not visible or writable by another user.
- Search uses indexed metadata fields and stays responsive for normal single-server use.
- Old files with no metadata remain accessible and searchable by filename.

## V6.9-B: Quotas and Usage

### Scope

- Display per-user used bytes, file count, and configured quota.
- Enforce per-user byte, file-count, and daily-upload limits on new uploads and replacements.
- Add administrator overrides and an audit trail for quota changes.

### Accounting rule

Use the current `pre_file.uid` owner as the primary charging subject. A file counts once for that owner even when it has multiple shares. Guest uploads retain the current per-IP daily limit and should not be folded into a user quota until there is a clear guest-accounting policy.

Before hard enforcement, provide a report-only mode for at least one release cycle. It exposes mismatches in old data and gives administrators time to set sensible limits.

### Data model

- `pre_user_quota`: `uid`, `byte_limit`, `file_limit`, `daily_upload_limit`, `updated_by`, `updated_at`.
- `pre_user_usage`: `uid`, `used_bytes`, `file_count`, `updated_at`.

Usage updates must run transactionally with file creation, replacement, restore, trash, and purge. A scheduled reconciliation command should be available to rebuild usage from `pre_file` where `deleted_at IS NULL`.

### Acceptance

- An upload over quota is rejected before storage transfer whenever size is known.
- Replacing a file accounts for the byte delta correctly.
- Moving a file to the recycle bin releases quota only if the configured policy explicitly says so; default recommendation is to keep it charged until final purge.
- Reconciliation can detect and repair stale counters without deleting content.

## V6.9-C: Scoped, Revocable API Keys

### Scope

Replace the site-wide API token with application keys while preserving it as a deprecated compatibility fallback for one major release.

Each key should have a name, public prefix, one-time secret display, hashed secret, scopes, expiration, optional IP/CIDR restrictions, request/byte limits, last-used time, and revoke state.

### Initial scopes

- `files.upload`
- `shares.create`
- `files.read_metadata`
- `files.delete_owned`

Do not introduce a broad administrator API key in the first version. Sensitive operations remain in the browser backend with administrator audit controls.

### Data model

- `pre_api_key`: `id`, `uid`, `name`, `key_prefix`, `secret_hash`, `scopes`, `expires_at`, `ip_rules`, `request_limit`, `daily_traffic_limit`, `last_used_at`, `revoked_at`, `created_at`.
- `pre_api_key_usage`: key/date request and byte counters.

### Acceptance

- Raw key secrets are never stored or shown again after creation.
- A revoked or expired key immediately fails without affecting other keys.
- Existing `X-Api-Key` callers can migrate gradually under documented compatibility rules.
- Audit logs record key creation, revoke, use failure, and scope-denied events without recording secrets.

## V7 Candidate: Upload Requests

An upload request is a dedicated upload-only link with an owner, expiry, file limits, optional password, optional form fields, and an inbox state. Contributors can upload but cannot list, download, delete, or discover existing files.

This should follow V6.9-B because each received file needs an explicit owner and quota charge.

## Explicitly Deferred

- Desktop sync, virtual drives, and conflict resolution.
- Online document editing and office-suite integration.
- Mandatory OCR, video transcoding, or antivirus scans in PHP requests.
- Elasticsearch/OpenSearch as a mandatory dependency.
- Physical folder moves across storage providers.
